# 🩺 불변식 게이트와 변이 테스트 — 게이트가 그린인데 결함이 있던 이유

## 💡 핵심 요약
v7.3.8 감사에서 이상한 일을 확인했어요: **기존 게이트 6개가 전부 그린**이었는데
그 안에서 **침묵 오답 2건**이 살아 있었어요(`bl`→rbp 오매핑으로 프레임 포인터가
오염되는데 `unsupported=[]`, 그리고 RET 없이 잘린 명령 스트림을 "완주"로 보고).
게이트가 거짓말한 게 아니라, 게이트가 **기능만** 물었기 때문이에요 — "이 함수들이
맞게 craft 되는가?" 픽스처에 그 결함을 드러내는 함수가 없으면 게이트는 영원히
그린이에요.

그래서 두 가지를 분리했어요:

| | 기능 게이트 (기존) | 불변식 게이트 (신규) |
|---|---|---|
| 묻는 질문 | 이 입력들이 맞게 나오는가 | **이런 실수가 구조적으로 가능한가** |
| 예 | `idiv3(30)==10` | 별칭 표가 두 벌인가 / 절단이 침묵 완주하는가 |
| 픽스처 의존 | 높음 (픽스처에 없으면 못 잡음) | 낮음 (규칙 자체를 검사) |
| 도구 | `test_n3_craft`·`test_n4_muldiv` | `test_audit_structural` |

그리고 **게이트 자체를 변이 테스트로 검증**했어요. 통과하는 게이트는 아무 정보가
없어요 — 원래 결함을 되살렸을 때 **정말로 빨개지는지** 봐야 해요.

## 🔩 기계 증명한 7가지 불변식 (`tools/test_audit_structural.py`, 47/47)
1. **단일 출처** — `craft_engine._ALIASES is x86_cf_emu._ALIASES`(값이 아니라 **객체
   동일성**). 사본은 "같아 보여도" 한쪽만 고치면 갈라져요. + 소스에서 다른 모듈이
   별칭 표를 독자 구성하면 실패 + x86 명명 규칙으로 **독립적으로** 유도한 참조 표
   68개와 전수 대조(에뮬레이터 표를 베끼면 결함도 함께 베껴서 검사가 무의미해져요)
   + 참조 표에 **없는** 이름을 알아보면 그것도 실패(허위 별칭 `sl` 이 정확히 이 경우).
2. **절단 = 침묵 완주 금지** — 알려진 모든 픽스처 함수(17개)를 **모든 절단점**
   (170개)에서 잘라 `unsupported` 가 비어 있으면 안 돼요. 한 함수의 끝 몇 개만
   보던 수동 검사를 성질(property) 검사로 일반화.
3. **캡은 흔적을 남긴다** — 한도는 이름있는 상수(`_INSN_CAP`/`_DEC_LINE_CAP`)여야
   하고, 익명 숫자 캡(`[:24]`·`guard < 16`)은 금지, 잘림 플래그가 **그 상수를
   참조**해야 해요(숫자를 다시 쓰면 상수와 갈라져요). 캐시 키도 고정 리터럴 금지.
4. **문서-코드 일치(행동 기반)** — 독스트링이 주장하는 명령 37개를 **실제로
   실행**해서 `unsupported` 가 비어 있는지 확인(거짓 주장 금지), 반대로 깨끗이
   실행되는 명령이 문서에 없는지도 확인(staleness 금지). 텍스트 대조가 아니라
   실행이라 주석 오타에 속지 않아요.
5. **문자 오염** — 한글 산문에 일본어 가나, 또는 한글을 **대체**한 한자 금지.
   단 정당한 국어 한자 병기(`무패(無敗)`·`세 적(敵)` 11종)는 허용 — 이 구분을
   안 하면 올바른 표기를 파괴해요.
6. **두 oracle 경로 일관성** — 직선경로 `_W` 와 cf경로 `_tdiv`/`_tmod` 가 같은 C
   truncation 이어야 하고, `_W` 산술 **649건**을 독립 참조(파이썬 int + 폭 마스킹)와
   대조해요. 던더 **존재**만 확인하면 `__mul__` 이 덧셈을 하는 침묵 오답을 놓쳐요.
7. **기록 정직성** — `record` 는 match 100% 만 저장(99.99% 도 거부). 엔트리를
   손으로 만들지 않고 **실제 파이프라인**으로 생성해요(손 dict 는 스키마가 갈라지면
   KeyError 로 터져서 "정직성"이 아니라 "내 dict 모양"을 재게 돼요).

### 판정은 4가지예요 — `rc != 0` 이면 잡은 게 아니에요
- 🟢 **CAUGHT** 게이트 실패 + **기대한 그 검사**가 실패 목록에 있음
  (기대한 검사가 아니면 🟠 **딴 이유** — 우연히 빨개진 것과 구분해요)
- 🔴 **MISSED** 게이트 통과 → 그 결함이 다시 살아도 아무도 몰라요
- 🟡 **CRASHED** 실패는 했는데 `❌` 검사 실패가 0건 → 검사가 잡은 게 아니라
  import/예외로 부러진 것. 실제로 겪었어요: `__mul__` 만 지우면 다음 줄
  `__rmul__ = __mul__` 가 NameError 를 내서 rc=1 이 나오는데, 그건 "결함을 잡은"
  게 아니라 "게이트가 부러진" 거예요.
- ⚠️ **ANCHOR** 변이 앵커 문자열이 파일에 정확히 1번 없음 → 리팩토링으로 어긋남.
  **조용히 skip 하지 않고 실패로 보고**해요. 실제로 두 번 울었어요: 제 문서를
  고쳐서 M11 앵커가 2건이 됐을 때, 그리고 `_div` 위임 리팩토링이 M9 앵커를
  다른 파일로 옮겼을 때. 둘 다 커버리지가 소리 없이 사라질 뻔한 순간이었어요.

### 게이트 자신의 구멍 7개 (변이 테스트가 찾아낸 것)
**가장 중요한 발견은 언제나 "못잡음"이에요.** 통과하는 게이트는 아무 정보가 없어요.

1. **M4b** — 던더 *존재*만 확인하고 곱셈 *정확성*은 확인하지 않았어요.
2. **M10** — 부호 유추(`_c_signedness`)를 아예 검사하지 않았어요.
3. **M11·M12** — 문자 오염 검사가 가나·한자만 보고 라틴 다이어크리틱을 못 봤어요.
4. **M17** — `_reg_info` 위임 검사가 *텍스트* 일치여서, 함수를 다시 인라인으로
   펼쳐도 **독스트링에 공유 구현 이름이 남아 있으면 통과**했어요.
   → 동일 객체 별칭 + `is` 검사로 승격. **텍스트 일치는 주석에 속해요.**
5. **N3-1** — "import 거부" 검사의 입력이 `import os`\n`def fn(x):` 였는데, 이건
   `len(tree.body) != 1`(문 2개) 규칙에서 **먼저** 거부돼요. 그래서 import 금지
   규칙을 통째로 지워도 검사는 통과했어요 — **검사가 자기가 시험한다고 주장한
   경로에 도달하지 못한** 거죠. → 함수 *본문 안* import/from-import/global 케이스
   추가(교훈: 입력이 그 분기에 도달하는지까지 확인해야 해요).
6. **N3-2** — 오프라인 게이트에 코드펜스 추출 경로 검사가 **아예 없어서**
   `_CODE_FENCE` 를 무력화해도 조용히 통과했어요. 펜스 마커가 소스에 섞이면
   구문 분석이 실패해 **정답도 거부**되는 침묵 성능 저하인데도요.
7. **A-4** — `"환각" in sb and "지어내" in sb or "억지 추측" in sb` 는 파이썬
   우선순위상 `(A and B) or C` 예요. 그래서 **한 단어만 남아도** 정직 계약 검사
   전체가 통과했어요. → 마커 전부 전제 + 누락 이름 보고로 교체.

### 이번 확장 자체가 드러낸 함정 3개 (가장 비싼 교훈)
**(1) 단일 출처화(DRY)가 차분 검사를 tautology 로 만들어요.**
`_W._div` 에 들어 있던 C truncation 구현을 `c_synthesize._tdiv` 로 위임시켰어요
(복제 제거, 차분 3,600건 + 실제 `_W` 224건으로 동치 증명). 그런데 게이트의
검사가 "직선 `_W` 나눗셈 == `SYN._tdiv`" 였어요 — 위임 뒤엔 **양쪽이 같은 함수**라
무조건 통과하는 tautology 가 됐죠. 게다가 649건 독립 참조 행렬에는 `+ - * & | ^ ~ <<`
만 있고 **`/`·`%` 가 없었어요.** 결과: `_tdiv` 를 바닥나눗셈으로 바꾸는 변이(M9)가
게이트 전체에서 안 잡히는 상태. → 참조를 **게이트 안에서 독립 유도**한
`_ref_c_div`/`_ref_c_mod` 로 바꾸고 삼방 대조(직선 · cf · 독립 참조, 132쌍 × 4) +
행렬에 `/`·`%` 추가(649 → **759건**). 이제 M9 는 5/5 결정적으로 잡혀요.
> 구현을 단일 출처로 만드는 것과 검사를 독립 참조로 만드는 것은 **서로 다른
> 의무**예요. 전자를 하면 후자가 자동으로 깨질 수 있어요.

**(2) 바이트코드 캐시가 변이를 되살려요 — sha256 복원 검증만으로는 부족해요.**
M9 검출이 실행 사이에 뒤집혀서(어떤 때는 CAUGHT, 어떤 때는 MISSED) 원인을
실측으로 좇았어요. 파이썬의 `.pyc` 무효화 기준은 `mtime(초 단위) + 파일 크기`인데,
**크기가 같은 변이**(M4b: `*` → `+`)를 되돌리는 것이 같은 초 안에 일어나면
캐시가 "변경 없음"으로 판단해서 **복원된 소스 대신 변이된 바이트코드를 실행**해요
— 14/14 재현했어요. 저장소 `__pycache__` 를 확인하니 실제로 오염돼 있었어요
(소스는 정상인데 `_W(7)*_W(3)` 이 21 대신 10). 그래서 이전 변이가 뒤섞여 판정이
**양방향으로** 오염될 수 있어요(없던 검출이 생기기도 함). → 게이트를 돌릴 때
`PYTHONPYCACHEPREFIX` 를 **실행마다 새 임시 디렉터리**로 주고, 복원 뒤에 sha256
뿐 아니라 **행동 프로브**(알려진 정답 6개를 새 프로세스에서 계산)로도 확인해요.
> "원본 바이트로 복원했다"와 "원본 코드가 실행된다"는 다른 명제예요.

**(3) `set -o pipefail` + `grep -q` 는 비결정적이에요 (실제 배달 실패).**
live 재검증을 다시 돌렸더니 `fetch_ghidra_dist.sh` 가 exit 6 으로 실패했어요
(디컴파일된 C = 0개). 원인은 추측하지 않고 실측했어요: decompiler 수리 조건이
`ldd "$DECOMP" 2>&1 | grep -q "not found"` 였는데, `grep -q` 는 첫 일치에서 즉시
종료하며 파이프를 닫고 → `ldd` 가 SIGPIPE(141) 로 죽고 → `pipefail` 때문에
파이프라인 상태가 141 → **조건이 거짓** → 수리 단계를 조용히 건너뜀.
**20회 중 5회(25%) 재현.** → 출력을 변수에 담고 파이프 없이 `case` 로 판정
(20/20 결정적), 수정 후 배달 3회 연속 exit 0 + 디컴파일된 C 6개.
재발 방지로 `verify_windows_bootstrap` 에 불변식 신설(pipefail 스크립트에
`| grep -q` 금지, 49 → **51/51**) + 변이 W-2 로 등록.

### 스위트가 자기 자신을 잡은 사례
- 오염 샘플을 리터럴로 적었더니 게이트의 문자 오염 검사가 **이 스위트 파일 자체**를
  스캔해 베이스라인이 실패했어요 → 샘플은 코드포인트로 조립해요. 스캐너의 자기
  주석에 예시 문자를 리터럴로 쓰면 자기 자신을 잡아요.
- 워크플로 주석을 쓰다가 제가 일본어 토씨를 섞었어요 → 스캔으로 바로 잡아 수정.
  이 함정은 "고쳤다"고 끝나는 게 아니라 **쓰는 순간마다** 다시 생겨요.

## 🧭 배운 규칙 (정직 원칙의 확장)
- **"게이트가 그린"은 "결과물이 맞다"의 증거가 아니에요.** 픽스처 기반 게이트는
  픽스처가 덮는 범위만 보증해요. 불변식 게이트를 따로 둬야 해요.
- **게이트도 검증 대상이에요.** 통과하는 게이트는 정보가 없어요. 원래 결함을
  되살렸을 때 빨개지는지(변이 테스트) 확인해야 하고, 그 과정에서 게이트 자신의
  구멍이 나와요.
- **참조 표는 베끼지 말고 독립적으로 유도해요.** 구현을 복사한 검사는 같은 결함을
  함께 복사해서 항상 통과해요.
- **절대값 불변식은 표류해요 → 상대 불변식으로.** `verify_ghidra_facts` 의
  "엉터리 쌍 코사인 < 0.2" 는 vault 성장으로 0.227 이 되어 **실패하고 있었어요**
  (dist 가 없어 rc=3 정직 skip 이라 가려져 있었음). 같은 파일의 주석이 이미
  "불변식은 낡은 상수가 아니라 같은 런 안의 차이"라고 말하고 있었는데 그 검사만
  절대 상수였죠. 시스템 자신의 기준(`cos_min=0.45`) + **최근린보다 낮은가**로
  바꾸니 판별력이 훨씬 강해졌어요(0.227 vs 최근린 0.998).
- **단일 출처화와 검사 독립성은 서로 다른 의무예요.** 구현의 복제를 없애려고
  위임시켰더니, "두 경로가 같은가"를 보던 검사의 양쪽이 **같은 함수**가 되어
  무조건 통과하는 tautology 가 됐어요(M9 실측). 검사의 참조는 게이트 안에서
  **독립 유도**해야 하고, 호출 관계가 있으면 안 돼요.
- **"원본 바이트로 복원했다"와 "원본 코드가 실행된다"는 달라요.** 바이트코드도
  캐시예요. 크기가 같은 변이를 같은 초 안에 되돌리면 `.pyc` 가 재사용돼서 변이가
  되살아나요(14/14 재현). 캐시를 격리하고, 복원은 **행동**으로도 확인해요.
- **셸 파이프는 비결정적일 수 있어요.** `set -o pipefail` 아래 `... | grep -q` 는
  `grep -q` 의 조기 종료 → 앞 명령 SIGPIPE(141) → 조건 거짓(20회 중 5회 재현).
  판정은 파이프 없이 해요.
- **검사가 시험한다고 주장한 경로에 입력이 실제로 도달하는지 확인해요.** "import
  거부" 검사의 입력이 더 앞의 규칙에서 먼저 거부되고 있어서, 금지 규칙을 지워도
  통과했어요(N3-1).
- **캐시와 캡은 침묵하면 안 돼요.** 고정 캐시 경로는 내용이 바뀐 바이너리를 같은
  이름으로 다시 채집할 때 **이전 분석을 침묵 재사용**해요(live 검증에서 실제로
  겪음). 캐시 키를 내용 해시로 만들고 출처(`source_sha256`)를 데이터에 기록하니,
  데이터가 스스로 "내가 어느 바이트에서 나왔는지" 말해요.

## 🔬 live 검증 (`tools/verify_gather_flags.py`, 20/20)
감사에서 "py_compile 까지만 검증했다"고 정직 고지했던 두 항목을 실제 Ghidra
(dist 배달 + PyGhidra)로 닫았어요:
- **③ N3 픽스처 충실성** — `SPECIMEN_C` 를 gcc -O0/-O2 로 재컴파일 → live Ghidra
  채집 → **6개 함수 명령 행렬이 픽스처와 완전 일치**, 전부 RET 종결,
  `classify` 실제 17명령·RET 종결 = 복구한 픽스처와 동일.
- **⑤ 캡·완전성 플래그** — 캡을 넘기는 함수를 의도적으로 만들어 `insns_complete=False`
  (명령 64 == `_INSN_CAP`)·`decompile_truncated=True`(C 120줄 == `_DEC_LINE_CAP`)가
  **정확히 캡과 일치**하게 찍힘을 확인. 작은 함수는 True/False 로 조용함(과잉 보고 금지).
- **시행착오로 배운 것** — 산술 연쇄 1500개나 `volatile` 누산은 Ghidra 디컴파일러가
  **하나의 거대 중첩 표현식으로 접어요**(10,276자지만 112줄) → dec 캡을 못 넘겨요.
  이때 `decompile_truncated=False` 는 **플래그가 맞고 specimen 이 틀린** 경우였어요.
  `if` 연쇄는 표현식으로 접히지 않아 줄 수가 실제로 늘어요.
- 선행조건(gcc·Ghidra 설치·pyghidra)이 없으면 **추측하지 않고 rc=3 정직 skip**.

## 🚧 남은 한계 (정직 고지)
- 변이 스위트는 **오프라인 게이트 7개 전부**를 검증하지만, live Ghidra 가 필요한
  `verify_gather_flags`·`verify_ghidra_facts` 는 선행조건이 없으면 rc=3 정직 skip 이라
  변이 판정이 불가능해요 → 대상에서 제외(그 두 게이트의 자기효능은 **미측정**).
- 게이트당 변이 수는 고르지 않아요(SLM 1종, win 2종 vs 구조 20종). 커버리지가
  얇은 게이트는 결함 한 종류만 되살려 봐요.
- `audit_brain` 의 정직 검사는 본질적으로 **산문 계약**(문구 존재)이라, 문구를
  정당하게 고쳐도 실패해요 — 그때는 마커 목록을 의식적으로 갱신해야 해요.
  환각 방어의 **행동** 검증은 `test_n3_slm_online`(변이 SLM-1)이 담당해요.
- 불변식 게이트는 `brain_engine` 의 레지스터/캡/문서/문자/경로 일관성을 다루고,
  SLM 브리지·quest·gardener 의 불변식은 여전히 기존 게이트(기능 중심)에 의존해요.
- `_W` 의 `>>` 는 논리 시프트예요. 이건 **결함이 아니라 일관된 동작**이에요 —
  직선경로에 오는 `>>` 는 oracle 의 `SHR` 번역이고(signed 우측시프트는 gcc 가
  `SAR` 을 내고 `SAR` 은 `_OPS` 에 없어 cf 경로로 떨어져요), oracle SHR 과
  9입력×2부호 전수 대조로 0불일치를 확인했어요.
